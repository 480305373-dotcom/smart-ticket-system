# 容量压测与结果解读

压测针对本机 `smartticket-cluster` 隔离部署，经过 Nginx、Gateway、注册发现、业务服务、PostgreSQL 与 Redis。不会创建或删除工单，不请求大模型，不把被限流的请求当作成功吞吐量。

## 运行

先启动标准分布式环境，然后在项目根目录执行：

```powershell
.\scripts\start-distributed.ps1 -SkipBuild -SkipImageBuild
python scripts/capacity_benchmark.py --stages 1,4,8,16 --duration 20
```

使用现有开发演示账号，密码只在进程内用于登录，不写入报告。可以通过 `BENCHMARK_USER` 与 `BENCHMARK_PASSWORD` 指定同类测试账号。工具仅允许访问本机 HTTP 地址，且要求标准部署的两个核心实例正在运行。

## 测试过程

1. 使用正常配置验证每用户每分钟 120 次的限制确实返回 HTTP 429。
2. 临时叠加 `compose.capacity.yaml`，仅把核心服务限流阈值提高到每用户每分钟 120000 次。JWT、资源权限、Redis Lua 限流以及数据库访问均保留。
3. 等待两个核心实例实际接到请求，预热后逐级增加并发。
4. 每个请求线程复用自己的 HTTP 连接，按 50% 工单分页、25% 工作台统计、25% 知识列表发送真实请求。
5. 记录成功吞吐量、所有 HTTP 状态、传输错误、成功请求 P50/P95/P99 延迟、全部请求 P95 延迟和测试前后容器资源快照。
6. 无论测试是否成功，都恢复标准 Compose 配置，并检查临时限流阈值已经移除。

临时配置会重建这组核心容器，8090 入口在实例切换期间可能短暂不可用。原开发环境和 8088 部署不受修改。进程被强制终止、系统断电时无法执行 `finally`；此时重新运行标准启动命令即可移除压测覆盖配置。

## 验收与边界

输出为 `docs/capacity-verification.json`。每档负载要求错误率不超过 1%、成功请求 P95 不超过 2000 ms；这是本项目的验收门槛，不是对外服务承诺。HTTP 429、非 200 响应和传输错误都计入测量阶段错误率。

采用闭环并发模型：每个线程收到上一次响应才发下一次请求。它能建立当前环境下的可重复基线，不能替代固定到达率的峰值流量测试。报告中的吞吐量只适用于当次 CPU、内存、数据规模、缓存状态和同机资源竞争；它是已经测到的下限，不代表系统最大容量。

当前工作负载仅包含读取。写入、索引同步、AI 生成和跨机器网络需要分别设计专项测试，不能共用这里的吞吐量数字。
