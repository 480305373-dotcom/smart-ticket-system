## 五分钟演示

1. 按 README 启动 PostgreSQL、dev 后端和 Vue，使用 dev_zhangsan / Demo@12345 登录。展示 Dashboard 与我的工单，说明数据来自 PostgreSQL。
2. 创建“VPN认证失败”工单，说明现象并选择优先级。展示 OPEN 状态、CREATE 历史、关键词推荐，添加留言。
3. 换另一浏览器会话，用 dev_lisi 登录并访问该工单地址，展示后端 403；访问管理员路径会跳回概览。
4. 用 dev_admin1 登录，打开该工单，指派给自己。进入“分配给我的工单”，找到记录；返回详情，开始处理、回复、关闭，展示状态和指派历史。
5. 回到普通用户会话刷新，查看处理人、管理员留言及关闭结果。管理员创建知识草稿，普通用户访问显示未发布；管理员发布后普通用户可阅读。

## 讲解重点

**权限在哪检查？** JWT 过滤器验证签名、过期和撤销状态，SecurityConfig 控制公开与管理入口；Controller 校验管理员操作，Service 校验工单归属。普通用户直接构造 HTTP 请求也无法绕过工单权限。

**为什么状态更新需要事务和条件？** 从 OPEN 读取后，另一个事务可能已开始处理；UPDATE 同时匹配 id 与旧状态，只有成功更新一行才写历史。状态和历史在同一事务里提交。并发测试验证两次处理只有一次成功。

**为什么单独做请求表？** `(user_id, request_id)` 唯一键由数据库决定哪次请求获得创建权。重复请求等待首次事务结束后读取结果；内容摘要阻止同一编号用于不同正文。历史写入失败时连同请求认领与工单一起回滚。前端按钮禁用改善交互，服务端约束保证并发请求的正确性。

**为什么处理人只允许管理员？** 当前权限模型中 USER 是报障人，ADMIN 是服务团队。指派不改变创建人和普通用户的可见范围。若扩展专门的处理人员角色，需要另行设计角色和数据权限。

**推荐是不是 AI？** 当前只做关键词、分类、标题匹配，排序后返回最多三篇已发布文章。没有 Embedding、语义检索或大模型生成；原项目的 AI 扩展保留但 dev 验收不启用。

**查询优化如何证明？** 看 UserDirectoryService 的 IN 批量查询、TicketMapper 的统计 SQL，以及 ArticleService 只加载命中文章正文。前端构建按组件分块。当前没有压测结论，不承诺吞吐量或数据库耗时。

**验证证据在哪里？** TicketBusinessTests 验证真实数据库业务，TicketConcurrencyTests 验证两个独立事务，TicketTransactionTests 注入历史故障检查回滚，JwtFilterTests 检查过期和故障响应。scripts 下可重复执行 HTTP、浏览器和数据库验证；实际结果见验收报告及 JSON 清单。
